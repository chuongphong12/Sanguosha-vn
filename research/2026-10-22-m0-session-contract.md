## Findings that change the integration plan

1. The existing engine contracts can be reused, but there is no unified playable battle state or registered Quốc Chiến game. Setup completion, scheduler acceptance and a complete match are different boundaries.
2. A durable database adapter alone does **not** provide the approved persist-before-success-visible guarantee. Installed boardgame.io broadcasts a state update before its storage writes complete.
3. Default missing-match sync can create a match; default credential authentication depends on metadata having credentials. The release must explicitly reject unknown/deleted IDs and prevent late writers from recreating deleted state.
4. Stock leave/presence semantics are not the selected human-membership semantics. Metadata names, sockets, living generals, bot control and reserved reconnect rights must be distinguished.
5. A single outer session command/view seam should route the already distinct engine request families. Card-use admission is not a generic adapter for trigger prompts, direct card requests and simultaneous batch/race collection.

These are source observations and design implications. They are not demonstrated production exploits, benchmark results or completed runtime repairs.

## Dependency behavior that the adapter must address

### Publication precedes persistence today

**B 3407–3425** authenticates a move against metadata; **B 3468–3489** checks activity, move permission and `_stateID` (unless the move opts out). After reducing the action, **B 3496–3512** invokes the subscriber and sends update/patch. Only afterwards, **B 3525–3537** writes state and metadata, separately for asynchronous stores.

Inference: adding Postgres/another durable store under the stock master does not prevent clients from seeing state that has not committed. It also does not supply one transaction spanning membership, gameplay state and metadata. A custom session/master/transport boundary or equivalent staged-publication integration must demonstrate commit before authoritative success publication. Merely awaiting the final `onUpdate` promise at the caller is insufficient because the internal send has already happened.

### Missing-match creation and deletion are unsuitable defaults

**B 3544–3586** fetches state/metadata/log/initialState and creates a match on demand when state is missing. Default Auth's `shouldAuthenticate` is false when metadata lacks credentials (**B 2877–2893,2926–2930**). Therefore the adapter must reject deleted/unknown match IDs before generic sync/create behavior, authenticate every protected seat operation independently of a missing record, and make explicit creation the only path that allocates a new room ID. A future game requiring setup data might stop one branch, but that is not a complete revocation contract.

Default lobby Leave deletes a named player's metadata then wipes only if no metadata player name remains (**B 2302–2332**). That tests names, not humans remaining, grace reservations or bot control. `InMemory.wipe` deletes only state and metadata (**B 2678–2681**), leaving that adapter's initial/log maps; `FlatFile.wipe` deletes state, initial, log and metadata (**B 2802–2809**). Full privacy deletion must enumerate and purge all private stores, including bot memory, command receipts and pending notifications if introduced. This is a contract gap, not a claim that a specific deployed database currently retains accessible data.

### Queue and connection metadata do not solve membership races

SocketIO update actions use an in-process per-match concurrency-one queue (**B 3901–3905,3943–3948**). Sync/connection-change handlers and lobby join/leave are separate paths (**B 2256–2332,3907–3927**); the queue alone does not serialize them with actions or coordinate multiple processes. An empty socket room removes its queue/client list, not the stored match (**B 3833–3846**).

Every authenticated connection change assigns one `isConnected` boolean to the seat and broadcasts before saving metadata (**B 3606–3647**). Each socket disconnect calls that method with false (**B 3921–3927**), even if another tab for the same seat remains. Presence should be derived from that seat's authenticated connection set; decision control is a separate single-owner concept.

The application currently blocks fresh joins once `G.status !== "waiting-room"` (`server/server.ts:34–42`). Its explicit leave action calls the legacy lobby route, catches errors and redirects (`MainScreen.ts:654–674`). Credentials are taken from history state or legacy URL parameters (`MainScreen.ts:223–237`; `src/main.ts:45–46,107–115`), which does not establish the approved same-browser durable return store. Room invitation URLs must not inherit the credential-bearing legacy path.

## Proposed minimum session shape

**Recommendation for design review, not implementation:** one private room/session authority around the existing engine operations; one outer command-to-committed-view seam, with distinct typed decision routes inside it.

### Canonical state, not a permanent intersection of fixture objects

| State category                      | Proposed canonical owner                                                                                                                                | Persistence/view rule                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Room lifecycle and human membership | Room/session record, with explicit room generation and revision                                                                                         | Survives restart while valid; only allowed public membership labels enter views. Presence sockets are ephemeral and reconstructed.                                                 |
| Before battle                       | Existing paired setup domain                                                                                                                            | Existing setup methods/projection remain usable. Persist selected setup and version identity until provisioning completes.                                                         |
| Battle                              | One canonical engine data object with physical zones/resources, HP/alive/identities, flags/marks/history, turn/phase, results and pending runtime state | Atomically provision from completed setup once; do not keep two independent mutable HP/alive/actual-general authorities. Derive any compatibility facade from the canonical owner. |
| Scheduler                           | Persisted scheduler alongside the exact engine state it describes                                                                                       | Frames/continuations/shared data/reservations/RNG must match one revision. Registry code is reconstructed from matching immutable registry/manifest/rules/schema identities.       |
| Decisions and control               | Actor-private pending requests plus seat controller generation/decision identity                                                                        | Same authenticated actor gateway for human and bot; control generation fences late jobs/replies. Batch/race membership has its own normalized collection authority.                |
| Output                              | Recipient-labelled notifications and deduplication identity associated with the accepted revision                                                       | Stage effects until commit, then publish filtered state and private notices. Do not do irreversible network delivery inside a rules callback before persistence.                   |

Alternative A, retaining setup plus every operation fixture's independently mutable fields permanently, is quick to assemble but makes stale HP/alive/general mirrors possible. Alternative B, rewriting every operation around a brand-new session interface immediately, has a much wider blast radius. The proposed setup-to-battle provisioning and private runtime adapters reuse current code while giving each fact one owner. Actual shape and write-through adapter boundaries require prototype evidence.

`CardCommandGame.currentPlayer` is non-null (`card-command.ts:30–34`) while combat supports a nullable current player (`damage.ts:34–40`). Narrow a facade at a validated command context; do not erase the nullable between-turn/terminal state solely to satisfy an interface intersection. Likewise, Hegemony `gameResult` must be mapped deliberately to session completion and boardgame.io's terminal state instead of inheriting the old `G.winner` endIf.

### Public and private command routing

1. Load the room by explicit existing ID/generation; reject a deleted/unknown room. Authenticate the guest seat independently of client-claimed player IDs. Resolve its current controller and expected room/decision revisions.
2. Deduplicate request identity and serialize the command with join/leave/presence/deletion/timeouts under the same room authority. A process-local queue can assist one owner; cross-owner writes still require storage fencing/compare-and-swap or an equivalent single-writer lease.
3. Route setup choices to the setup contract; targetful card-use choices to existing card-command admission; trigger order/step choices to validated scheduler resume; direct acquisition and race/batch replies to their corresponding method-specific authorities. Never accept arbitrary operation names, card descriptors or raw frames from the client.
4. Advance actual engine children to a valid checkpoint: completion, a pending decision, or a structured interruption whose eager effects remain represented. Persist all corresponding state, request receipt and staged outputs consistently before success becomes visible.
5. Publish only the seat's projection/choices and recipient-permitted notices. ACK means durable acceptance, not that the card/turn necessarily completed. On lost ACK, retry of the same request returns the committed result rather than paying costs again.

Existing `getTriggerPrompt`/card-command view are useful private components, not full battle projection. The new bot receives the same actor view plus actor-permitted legal offers/history; no raw Room, scheduler frames, deck order or shared per-bot knowledge. For local solo, a local authority/worker can use the same contract and a separately validated browser-durable adapter. Browser-local persistence is not server restart recovery, atomic multi-tab storage, unlimited quota, or cryptographic secrecy from the offline browser owner. A browser-owned solo match need not consume an online room slot, but that deployment/capacity assumption must be explicit in M0.4/M0.5 measurements; the five-server-room cap is not evidence of local storage safety or bot performance. Current MatchClient uses Local()/Local({ bots }) without persist (src/client/MatchClient.ts:70–79).

The request broker must preserve luck all-send/common-deadline and Nullification/race semantics. A registered collection adapter may suspend the engine while the outer room collects authenticated replies, but an internal broker checkpoint must not appear as a serial human prompt or bypass controller fencing. Its concrete bridge is a **M0.4 prototype design item**, not an existing deployed scheduler feature.

Structured native interruption and unexpected exceptions must remain distinct. Existing eager mutations cannot be rebranded as clean rejected commands or globally rolled back by assumption. Unexpected invariant failure must fail closed; the valid checkpoint/fault policy and operation-specific cleanup need M1 design/tests before release. This paper contract does not resolve native unwind by adding a database transaction.

## HITL decisions resolved on 2026-10-22

The source investigation exposed four policy gaps. The human answered Q25–Q28 in the parent session; the following resolutions replace the research recommendations. This closes those four policy questions, not M0.2 or any prototype gate.

| Decision                                     | Source or ambiguity                                                                                                                         | Accepted human resolution                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q25 — Roster and explicit departure          | Legacy server rejects fresh joins after waiting room; engine seats still own generals/cards after lobby metadata is removed.                | Roster freezes when paired setup begins. Fresh joins only before setup; authenticated returns to an existing retained seat during play remain allowed. Mid-match explicit Leave transfers that game seat permanently to a bot and revokes its credential if other online humans remain. Leave is not an engine kill/general-removal rule.     |
| Q26 — Last online human versus offline grace | A explicitly leaves while B has thirty seconds of grace. Initial research recommended preserving B; the human rejected that recommendation. | Last ONLINE human explicit Leave deletes immediately, revoking B's unexpired return rights. Passive all-offline departure instead receives sixty seconds; server downtime is not Leave. Connected participants, retained guest membership and living characters are distinct facts.                                                           |
| Q27 — Independent clocks                     | A prompt is fifty-nine seconds old when its actor disconnects.                                                                              | Original decision deadline and sixty-second disconnect deadline proceed independently, excluding server downtime. Neither resets the other. A one-off bot can answer the old prompt at second sixty before full seat takeover.                                                                                                                |
| Q28 — Multiple tabs                          | Stock isConnected is one boolean; state revision alone does not identify the intended controller.                                           | One controlling tab. Other authenticated tabs receive the same actor view read-only and can explicitly Take Control, fencing the previous generation. Automatically reclaim only when no active controlling tab remains; a background reconnect does not displace an active controller. Closing a secondary tab is not an offline transition. |

Room protection, seat return authorization and engine life status must stay separate. An offline retained credential permits return only while the room survives; it cannot veto the Q26 last-online explicit deletion. After offline takeover a human may still reclaim their seat while another human keeps the room alive. An explicitly departed human's revoked credential cannot reclaim the permanent bot seat. A dead human who remains connected is still an online human for room lifetime.

Vendor, storage technology, raw request payload shape, batching bridge and numerical latency/strength thresholds remain M0 research/prototype outputs. They are not additional product scope changes to ask the user to design without evidence.

## What can begin after review

- M0.3 can prototype the actor-only choice/policy/control seam independently of a full content inventory, using named actual operation cases and declared remaining authorities.
- M0.4 can prototype explicit create/join, staged commit/publication, real storage restore/delete, typed request collection and credentials. Its success needs real transport/store faults; a mock `setState` that always succeeds would miss the dependency-ordering problem.
- M1 still owns complete startup provisioning, remaining phases/turns, package registration and native unwind. M2 still owns the fully integrated desktop room and transport. This investigation does not move those implementations into M0 or claim a complete match.

## Installed extension seams and commit-before-publication feasibility

The runtime export probe returned Master from boardgame.io/master and FlatFile, Origins, Server, SocketIO from boardgame.io/server. The master subpackage routes to dist/cjs/master.js (master/package.json:2–6), which explicitly exports Master (:14–18); its declaration also exports Master (dist/types/packages/master.d.ts:1–2). Two viable prototype shapes follow from those seams:

1. **Application-owned session with a boardgame.io compatibility adapter.** Serialize every room mutation outside the stock lobby/master handlers; construct Master with per-command staged storage and buffered transport/subscriber effects. After it returns successfully, atomically commit the canonical room, state/log/metadata, receipt and outbox under revision/generation fencing, then release recipient-filtered output. Discard staged work on failure; recover committed outbox after a crash. A stock storage wrapper merely writing immediately cannot make its independent setState/setMetadata calls transactional (src/master/master.ts:268–313). Stock LocalMaster's subscriber starts bot work from raw state before persistence (src/client/transport/local.ts:104–121); do not carry that behavior into the fair bot seam. This shape preserves more client protocol but must implement and fault-test staging, unknown-ID rejection, transactional creation/deletion, lobby replacement, filtering and background-job fencing together.
2. **Application-owned session protocol around the Quốc Chiến operations.** The session itself advances validated dispatch/resume and stores the canonical room before publishing actor views; transport endpoints return that contract directly. As a throwaway control experiment this can run without stock Master; it is not approval to remove boardgame.io from the target stack. This removes State/ctx/move compatibility work but requires adapting the client subscription/action boundary. It does not require rewriting the rules operations, whose existing admission and scheduler interfaces remain inside the session.

Recommendation for M0.4 within the approved TypeScript/PixiJS/boardgame.io stack: prove the smallest real command → transaction → actor-view path using the first shape, with application-owned sequencing and staged Master storage/output. The second shape may serve as a bounded throwaway control experiment to isolate engine/session behavior; it is not the selected production replacement. If measurements suggest abandoning boardgame.io, record that as a new scope/architecture decision for the human before implementing such a change. Do not fork or mutate dependency bytes as an unreviewed shortcut, and do not advertise a stock custom-master config that 0.50.2 does not expose. Prototype results select concrete adapter details within the accepted stack; they do not silently change the stack.

Client visibility also needs an explicit constraint. The client middleware runs next(action) before transport.sendAction (src/client/client.ts:290–302); merely delaying server broadcast does not necessarily prevent optimistic UI state. Installed reducer supports long-form move client:false (src/core/reducer.ts:325–328). A compatibility prototype must disable authoritative optimistic rules execution and distinguish pending intent from committed success; an actor-view client should expose only committed outcomes.

Local persistence is a separate experiment. Local({ persist:true }) selects browser LocalStorage instead of InMemory (src/client/transport/local.ts:46–50,97–98,208–225); LocalStorage writes separate state/initial/metadata/log maps with synchronous localStorage.setItem (src/server/db/localstorage.ts:3–27,34–42). This establishes available storage mechanics, not atomic session commits across those maps, error handling, multi-tab fencing or approved deletion. Current local mode does not enable persist. Either chosen prototype must validate browser refresh/storage-failure recovery independently; online restart durability and the five-room server capacity target do not establish it.
