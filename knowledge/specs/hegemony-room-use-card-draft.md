## B: authenticated command and targetful request admission

See the [native request/client investigation](../research/targetful-command-admission.md). Strict web admission below is an additional authoritative contract; it must not be attributed to the weak native CardUseStruct::isValid method.

- Keep the scheduler's string/null reply contract. A registered request operation owns private reason, actor, pattern/method, add-history, request stage, selected canonical offer and ordered target prefix. It offers opaque tokens for card/material selection, eligible next targets and final confirmation. Tokens refer to private server-owned offers, never client card descriptors, flags, class names, resource identities or callback names. Only supported/versioned package metadata can supply offers; do not treat the existing Standard catalogue as Quốc Chiến content.
- A public command-submission wrapper obtains the actor from a trusted authentication adapter/context separately from the reply body. Missing/unbound identity, another actor's token, malformed reply, stale prompt/frame/registry, unsupported intent and replay reject without changing game, frames, history or cost. The authentication provider and actual boardgame.io/network binding remain outside this normalized slice; tests must identify the supplied adapter, not claim a deployed login implementation.
- For Play, require the eligible living active actor in Play according to private phase authority; capture/check the request's phase context. For response-use, bind to that request's expected responder and context without requiring it be that actor's Play phase. Response-use is a child operation inside an existing flow, not a second root dispatch while scheduler frames are active.
- Revalidate current selected offer on every intent-advancing reply and before execution: enabled supported metadata/version, skill ownership or native matching flag/TransferSkill exception where applicable, ViewAs eligibility, declared material-selection permissions and current accessible locations. Hand ownership alone is insufficient: equipment/private-pile materials can be allowed by trusted package policy. Never expose other actors' material IDs through request projections.
- Check target choices incrementally in order using package targetFilter/prohibition/max-vote policy, then final targetsFeasible. A target-fixed command submits no manual targets; implied recipients belong to its trusted card policy. The existing shared execution normalization uses unique targets; metadata requiring repeated/multi-vote target semantics is unsupported until explicitly modeled and must not be offered or silently collapsed. Alive/kingdom/distance rules belong to the specific card policy, not blanket native assertions.
- Back/cancel may discard an invalid selected offer or target prefix while request/authentication/scheduler freshness remain valid; they do not enter Room or spend history/cost. Superseded request-context replies still reject.
- Request state and offered tokens persist through JSON. Prompt IDs/generations rotate when a new prompt/retry is issued. A card-use request view exposes only the expected authenticated actor's permitted display labels and choice tokens; other actors/spectators receive null. Raw offers, hidden slot names, ledgers and frames remain private.
- Before executing, emit the applicable native ChoiceMade event and ignore its consumption/payload rewrite as the native caller does; retain the local selected use. Revalidate after this yielding event before entering Room wrapper as an explicit web policy, since earlier handlers can change permission/state. Do not charge cost or history before admission succeeds.
- Distinguish invalid submission (false, unchanged), accepted scheduler progress (true), cancellation/decline and Room use success. Scheduler dispatch/resume true is not a card-use result. On Room false, preserve its eager validation changes, refresh eligibility/offers and issue a fresh request according to the targetful request policy. Do not replay the old token, roll back a paid validation effect or re-run an already completed child.
- PlayCard/activation and targetful response-use reason/pattern/ChoiceMade behavior follow their native ownership. This operation does not create the complete phase/turn loop, pure response or direct MethodUse lifecycle. A completed request returns an explicit successful/declined result to its caller; the caller owns subsequent phase progression.

This design chooses the staged opaque-choice approach over a structured public payload/private inbox. It fits the already approved prompt seam and avoids adding mutable ingress inbox state or broadening scheduler replies. Package discovery/predicates remain explicit supplied authorities; the command module implements the authorization binding, freshness/material/ordered-target gates and actual dispatch/retry state machine.

## Interface and ownership

Add a private normalized `room-use-card` operation and factory in a focused module, separately named from existing `card-use` (Card::use). Entry contains a shared card-use descriptor, a registered private card reference and optional add-history boolean, defaulting to true. It is not an authenticated client command.

The operation owns its continuation stages, actual signed per-player card-history counters, m_addHistory/m_isHandcard lifecycle fields, repeated-Slash flag and generic ordering/branch decisions. History is private JSON state; missing history keys read as zero, malformed supplied data rejects. Do not clamp signed native history to nonnegative numbers or implement history as a test-only callback. The existing recipient flag storage can hold the repeated-Slash flag instead of introducing another player-flag authority.

Private authority resolves native parse/rebuilt reference, getRealCard identity, current handling method/limitations/recast availability, phase and class ancestry. Package validation and after-validation are registered child operations so their eager state changes and prompts can be serialized. Card-specific onUse dispatch selects the existing non-Skill, SkillCard or card-specific operation from trusted metadata. Exact normalized TypeScript shapes will follow existing operation conventions; none of these properties are accepted as public client claims.

Flag/tag copying must actually update private card-resource storage: apply incoming flags with native set-flag semantics to the parsed card, retaining unrelated parsed flags; replace its tags with a copied incoming map. For same-real one-material virtual DelayedTrick, implement the supported normalized wrapped-face transition before onUse, using trusted face metadata and the existing wrapped ledger. Preserve face/ID/flags/tags semantics and ordering of update notification before showSkill assignment; do not replace wrapping with a no-op fixture. Live native pointer allocation, full catalogue parsing and transport delivery remain adapters. Their supplied behavior and all fixture substitutions must be explicit in test/checkpoint claims.

Keep existing shared readers and both onUse envelopes unchanged unless a newly reproduced compatibility failure makes a change necessary and its impact is checked. No automatic routing of existing Nullification, Jink or rescue wrappers through this new operation.

## Required execution semantics

1. Capture the entry use and flags/tags; obtain the normalized reparsed reference and copy those flags/tags into its storage. Initialize m_addHistory false. Determine m_isHandcard from a nonempty physical-material set entirely owned by the original entry source in hand. Empty, mixed or non-owned materials make provenance false; provenance alone is not a rejection rule.
2. Reject only the native handling-method limitation/recast condition at this gate. Capture the original pre-validation history key (Lua ancestry uses `#` + objectName, otherwise class name) and the original source's sum of Slash/ThunderSlash/FireSlash histories before validation.
3. Run validation as an actual child. It can rewrite from/to/card and mutate game state, then return a card reference or null. Null returns false without history/onUse/after-hook; retain earlier eager child changes. Never treat false as a rollback guarantee.
4. If the post-validation source is in Play and this invocation's add-history is true, mark m_addHistory and increment that source's captured original key, then its returned-card ViewAsSkill key when nonempty. Native getSkillName's leading-underscore normalization applies; the key source and target source can differ because validation runs between capture and update. Ordered history notifications are an explicit private adapter following each actual state increment; delivery is external, never substituted for state mutation.
5. Compare the post-validation local card's real identity with the returned card through private identity authority, not JSON equality. In the same-real branch, perform any required DelayedTrick wrap, then repeated-Slash flag (captured count > 0 and add-history true, without an added Play-phase guard), then physical-wrapper update/reset notification. Dispatch card-specific onUse and then the local card's validateAfter using the wrapper's saved post-validation local use. Shared event rewrites from onUse must not replace that saved struct automatically; reference-backed mutable card metadata remains resolved through private authority.
6. In the conversion branch, save a new use with the returned card and recursively dispatch this operation with default add-history **true**, including when outer add-history was false. Ignore the recursive boolean result. Invoke the outer post-validation local card's after-hook with the saved outer converted use; inner local reparse/validation rewrites do not flow back into it. The outer call returns true when this normal path finishes, even if the inner call returned false.
7. Normal result is boolean only. Void onUse/after child return values must not replace use snapshots. Scheduler interruption freezes the remaining work, preserving already committed state/history/cost; no fabricated normal finish or after-hook. The native catch/unwind sequence is not claimed by this slice.

The after-hook receiver here is the **local card after validate may have rewritten card_use.card**. Do not generalize Nullification's separately captured raw-card after-hook to Room::useCard.
