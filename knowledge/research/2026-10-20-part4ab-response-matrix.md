## Finding

The next missing implementation is not another general-purpose targetful use command. Part 4aa already provides that normalized seam. The missing work is the distinct native direct-response lifecycles and their composition with already-present Slash and dying orchestration. Existing orchestration and fixture movement must not be reported as absent, or as complete askForCard implementation.

The native handling method must accompany the request: Slash defense asks Jink with MethodUse, ArcheryAttack asks the same Jink with MethodResponse, and Duel asks Slash with MethodResponse. A card name or a generic response-use reason cannot choose the lifecycle. Verified native definitions, callers, source hashes and branch details are in the [companion native investigation](2026-10-20-direct-response-native.md); the earlier [entry audit](card-admission-and-response-audit.md) remains historical context.

## Why existing envelopes are not interchangeable

`card-on-use` performs ordinary onUse target sorting, TargetSelected and its own evolving event snapshots. Direct askForCard(MethodUse) has a local original CardUseStruct plus a separate mutable event payload. Event payload rewrites can affect GameRule execution without replacing the local original-card after-hook arguments or the validated card used for material cleanup. It has no direct Room::useCard/history or Card::onUse invocation. See [pinned direct MethodUse](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1751-L1804) and [CardUsed GameRule](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/gamerule.cpp#L537-L614).

Shared `createCardUsedRule`/`createCardUsedOperation`, `createCardFinishedRule`, resources and movement are suitable existing implementations to compose. Their event consumption and original/current resource identity must remain observable. Calling common onUse as a shortcut would insert the wrong envelope even when an ordinary physical Jink fixture appeared to work.

## Proposed first slice: 4ab.1, direct MethodUse after validation

This is a bounded addition at the existing registered-operation seam. Three approaches were considered:

- **A — Add a dedicated post-validation MethodUse operation, recommended.** A trusted internal parent supplies responder, original parsed response and validated response/resource reference. The operation owns the direct event/movement/reveal/finish/cleanup/after lifecycle and returns the validated response. Reuse the real scheduler, movement and shared GameRule implementations. Input is server-internal, not a new client command. Catalogue selection, ChoiceMade and validation remain the parent's explicit responsibility for this slice.
- **B — Implement all askForCard acquisition, both handling methods and rescue integration together.** More immediately complete, but combines prompt/provide/retry state, two execution routes and a separate composite route. Harder to isolate native snapshot and resume failures; defer until the first execution contracts have independent evidence.
- **C — Forward direct responses into the 4aa Room/onUse path.** Reject: inserts ordinary onUse/history/target processing and loses native lifecycle distinctions. Reusing the scheduler and shared GameRule is appropriate; replacing the envelope is not.

### Proposed interface and authority split

A new private factory (working name `createDirectMethodUseOperation`) registers one serializable operation. Its input contains a known responder and distinct original/validated card descriptors with registered references. Optional rich card metadata is retained. The parent must already have completed response validation, physical wrapped-card synchronization, method-specific logging and ChoiceMade. Table/discard destinations and source-backed reveal/notification and original-card after-hook operations are configured privately, outside continuations. A private reference authority supplies current validated-card metadata/material IDs when needed; table filtering and actual movement remain the module's implementation. Actual function/type names can follow current conventions during implementation without changing this contract.

The module itself implements PreCardUsed, native material snapshots and movement, CardUsed, the finish versus suppression branch and remaining-table-material discard. It must not delegate that missing lifecycle to a fixture. Package reveal/Huashen and notification delivery remain explicit adapters; the regression should demonstrate a real existing reveal implementation where compatible and label any remaining package predicate/notification fixture.

The native default CardUseStruct initializes `m_isOwnerUse` and `m_addHistory` true but does not initialize `m_reason`, `m_isHandcard` or `index`; the direct branch does not assign them. Proposed JSON normalization: retain defined constructor defaults where represented, omit unspecified members from the initial packet, and never read an uninitialized C++ value as a normative boolean/enum. In particular, initialized m_addHistory does not authorize an actual history increment. This is an explicit normalized web contract, not binary/native undefined-behavior parity. See [constructor](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/core/structs.cpp#L238-L241).

### Acceptance cases for the first slice

1. **Direct execution and caller composition.** Dispatch the registered operation through the real scheduler; assert exact event order and absence of envelope-added TargetSelected, Room wrapper history and ordinary onUse/extraCost. Compose a real SlashProceed/JinkEffect/SlashResult caller with this lifecycle in place of the movement-only `ask-jink` fixture. Assert that the validated reply reaches its caller and the real materials move exactly once.
2. **Original/local versus shared event snapshots.** Distinct original and validated references, raw SkillCard conversion input, PreCardUsed/CardUsed/finish payload rewrites and consumption. GameRule sees its mutable event data; the original-card after-hook receives the captured local use, and cleanup tracks the validated card/materials. A rewrite must not accidentally charge another card or replace the returned validated reply.
3. **Finish and cleanup branches.** Normal CardFinished versus current local-card `cardNotTriggerCardFinished` suppression; flags, HegNullificationTargets, current living notification recipients and Slash Jink tag removal. Check wrapped/virtual references, zero/multiple materials, empty hand origin and materials moved away by child events. Initial table movement uses IDs captured after ChoiceMade and before PreCardUsed. Cleanup independently resolves current materials of the original validated card identity and filters those still on table; neither a changed event card nor a permanently frozen initial-ID list replaces that lookup. Exercise a current-material change via the private authority. Do not invent rollback or claim a fixed descriptor emulates mutable native pointers.
4. **Persistence and input integrity.** JSON pause/restore at events, movement, reveal and after-hook; wrong/stale/replayed/registry-mismatched scheduler replies cannot replay work. Unknown actors, malformed descriptor/reference or ambiguous material location reject at the relevant seam. Preserve rich original/validated metadata and ensure package callbacks receive copies. No client descriptor/ownership authority is created by this internal operation.
5. **Unchanged behavior and interruption limits.** Existing response, Nullification, SkillCard and Room wrapper suites remain green; no double history or token cost. Turn-broken/stage-change/game-over retain already eager effects and freeze unfinished frames under the current scheduler contract. Native exception unwind stays explicitly pending.

Tests belong at dispatch/resume and real caller-composition seams, not against a private helper. Before source edits, rerun exact-symbol impacts for any existing implementation being changed. A new factory does not justify modifying the high-fan-out shared descriptor readers or generic scheduler without separate evidence.

## Approved expansion for implementation

On 2026-10-20 the user chose to include **CardAsked/provide/acquisition/validation-null retry** in 4ab.1. The earlier post-validation-only recommendation above is superseded for this implementation slice. The accepted dispatch/resume and real SlashProceed composition seams remain unchanged.

The new `ask-card-use` operation owns the MethodUse request reason/pattern, CardAsked conditions and ignored consumption, one shared provided-card slot (including an explicit null value), continuing flag suppression/clearing, AI/provided limitation checks, response validation and retry, ChoiceMade and the direct MethodUse lifecycle. Retry resets skillName and provision to native defaults, retains other request fields and eager validation effects, and does not restore room reason/pattern after nested asks.

The private request adapter owns authenticated transport/catalogue admission, human parsing, AI DummyCard unwrapping and delay/timeout policy. Accepted-card notification owns physical wrapped update/reset delivery and method-specific log/emotion/broadcast. Skill notice, reveal/Huashen, actual-general movement metadata and notification transport remain named package adapters. Tests must distinguish these fixtures from the real scheduler, movement, GameRule/resource and caller implementations; no production request gateway is implied.

Normalize native limitation(null) safely: consume a provided null or a dead-actor empty slot, emit nil ChoiceMade and return null without calling the limitation predicate on null. A real provided card still takes precedence if the actor has died. Provider storage is room-wide, not scoped to one cursor; nested asks may consume it. Duplicate provision is invalid even when its first value was null.

MethodResponse, MethodNone/Discard, retrial execution and rescue integration remain subsequent work. `ask-card-use` rejects unsupported method/retrial inputs and the native forbidden MethodUse Slash pattern. No shared reader, scheduler or legacy Standard registration change is authorized by this slice. Native exception unwind remains deferred.
