# Part 4ab.3: MethodNone and MethodDiscard requests

Research dated 2026-10-20 at game HEAD `cc219dfd4a1df9290d5400fb558fc60a1ddedc96`, after MethodResponse implementation `ea8c98cd13224d26207458e281a127a3ba221e6d`, and canonical knowledge `cccb130a3fd2dc1fe80704239b9bcc27016f2d13`. ## Finding

MethodNone and MethodDiscard share the acquire/validate/retry shell already studied for [MethodUse](../engine/direct-card-use.md) and [MethodResponse](2026-10-20-method-response.md), but neither is a direct use/response execution envelope. MethodNone returns a selected validated card without automatic movement. MethodDiscard moves it directly to discard with S_REASON_THROW. Neither emits CardAsked or CardResponded, nor invokes either original-card after-hook. The complete native owner is [Room::askForCard, room.cpp:1610–1848](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1610-L1848).

The most important distinction for implementation: the discard branch calls **moveCardTo directly, not throwCard**. Substituting throwCard would add card-derived skill metadata or duplicate skill log behavior that this owner does not request.

## Exact shared acquisition contract

Every attempt delegates focus notification and sets the pattern and reason. Both methods set CARD_USE_REASON_UNKNOWN. CardAsked is guarded by MethodUse/MethodResponse, so it does not run for these methods even on the first attempt. A continuing flag is still cleared before acquisition. The room-wide provided slot has precedence, including explicit null and non-null provision for a dead actor; dead with no provision returns the no-card result. Human input remains separate from AI/provided handling. See [room.cpp:1614–1669](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1614-L1669).

For MethodNone, native `Player::isCardLimited` immediately returns false. An external generic limitation callback must not accidentally reject a None selection. MethodDiscard retains the existing provided/AI method-specific limitation behavior, with human parsing/admission at the trusted adapter. No second generic limitation check follows conversion. See [player.cpp:1744–1774](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/core/player.cpp#L1744-L1774). The existing safe normalization of null provided/dead replies can remain: do not call a non-null predicate on null.

Non-null selected cards still run `validateInResponse`; it can return a different registered identity or null. Physical validated cards still require wrapped update/reset notification before ChoiceMade. A nil selection emits nil ChoiceMade and returns null. Validation-null instead sets continuing, retains eager effects and retries without a ChoiceMade or after-hook for that failed conversion. Recursive retry retains actor, pattern, prompt, data, method, recipient and retrial flag but resets omitted skillName and provision options to defaults. See [room.cpp:1665–1683](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1665-L1683), [retry:1842–1847](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1842-L1847) and [defaults, room.h:421–424](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.h#L421-L424).

The five-argument skill-name overload forwards to MethodDiscard with null recipient, false retrial and false provision. The longer overload defaults to MethodDiscard too. Retain that distinction if a facade is later introduced; these are not defaults to MethodResponse. See [room.cpp:1604–1607](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1604-L1607).

## MethodNone

After validation and physical wrapped synchronization, no method-specific response log, emotion or broadcast runs. There is also no MethodDiscard request-skill log/notice. Native computes hand provenance, but this local boolean is not exposed or used by the None result path; the web operation need not invent a new CardResponseStruct or observable hand field. Emit accepted ChoiceMade for the validated current card, then return its identity. There is no owned-card skill notice, table/discard movement, reveal/Huashen, use/response/finish event, flag cleanup, history increment, validateAfter or validateInResponseAfter. Owner branch: [room.cpp:1685–1740](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1685-L1740), with the return at [1842](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1842).

Concrete caller: [Jushou, standard-wei-generals.cpp:839–856](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/package/standard-wei-generals.cpp#L839-L856) selects with MethodNone; its caller then uses equipment via Room::useCard or throws the chosen non-equipment. The request must not pay or discard first. This is evidence for an internal selection/result seam, not authorization to port Jushou content or its compulsory fallback policy in this slice.

## MethodDiscard

After wrapped synchronization, a **nonempty request skillName** emits `$DiscardCardWithSkill`, listing the validated card's then-current effective ID/subcards, and invokes the request-skill notice. An empty request skillName emits neither. This precedes ChoiceMade and is distinct from the later owned-card-skill notice used by MethodUse/MethodResponse; MethodDiscard does not enter that later branch. See [room.cpp:1696–1710](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1696-L1710).

After accepted ChoiceMade, construct `CardMoveReason(S_REASON_THROW, actor)` and call `moveCardTo(validated, actor, null, DiscardPile, reason, true)`. The reason has no injected card skill name, request skill name, general name or event name. ChoiceMade can mutate current validated-card materials, so resolve the current validated identity at movement time; do not freeze IDs from the preceding log. Do not follow a replacement event payload. See [room.cpp:1730–1736](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1730-L1736) and [two-argument reason constructor, structs.h:141–145](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/core/structs.h#L141-L145).

The moveCardTo overload delegates to one atomic movement containing all current subcards, preserving the explicit source actor, null destination player, discard destination and force-visible true. A zero-subcard virtual card is an immediate movement no-op. It does not first move to table. Existing real movement owns before/after movement triggers and mutable movement semantics; source backing is [room.cpp:4944–4970](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L4944-L4970). No additional card-consumption/after-hook follows; return the original validated identity after movement. isProvision does not suppress this discard branch.

Why not throwCard: its convenience overload populates skill metadata from the card unless a request skill is supplied; its implementation can independently emit `$DiscardCardWithSkill` before atomic movement. That would change the direct branch's observable behavior. See [throwCard, room.cpp:4873–4918](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L4873-L4918).

Concrete caller: [Xiaoguo, standard-wei-generals.cpp:1154–1169](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/package/standard-wei-generals.cpp#L1154-L1169) pays the Basic-card cost through the skill-name overload, then asks the affected player for an equipment discard using the default MethodDiscard. The caller owns later draw/damage; a returned non-null card is already discarded. A small composition test can model that contract without claiming the full package port.

## Retrial is a separate boundary

`askForCard(..., isRetrial=true)` is an **acquisition option**, not Room::retrial. It suppresses CardAsked, normal MethodUse/Response log/emotion/broadcast and their direct execution branch. It still performs response validation, physical wrapped synchronization, ChoiceMade and return/retry. MethodDiscard still discards when isRetrial=true because its branch precedes the `!isRetrial` guard. None remains no automatic movement. No validateInResponseAfter is called by these suppressed use/response entries. See the owning guards at [room.cpp:1633,1685,1733–1736](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L1633-L1736).

Actual [Room::retrial, room.cpp:7934–7978](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/server/room.cpp#L7934-L7978) takes the effective physical ID, replaces the judge card, moves the new card to the judge zone, and moves the old judge card to responder hand for exchange or discard otherwise. It logs ChangedJudge and performs both moves atomically. It dispatches CardResponded(isRetrial=true) only if the new effective card was owned by the responder at function entry; it captures that ownership and hand provenance before moving. Its response data is the default QVariant rather than the original ask data. Judge result update is explicitly not performed inside this method.

Package composition adds still more behavior. [Guicai cost/effect, standard-wei-generals.cpp:116–182](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/package/standard-wei-generals.cpp#L116-L182) acquires with MethodResponse/isRetrial=true, then owns invocation/logging, response-reason movement to table, CardResponded with request data and constructor-default isRetrial=false, and storage of a card string. Later its effect calls Room::retrial(exchange=false) and judge.updateResult. [Guidao cost/effect, standard-qun-generals.cpp:965–1031](https://github.com/TamQuocSat-LangKhach/QSanguosha-QuocChien/blob/ce4e62b31c4d1a65de79188be11ccdd4f0ac6f9f/src/package/standard-qun-generals.cpp#L965-L1031) does the corresponding black-card acquisition and calls Room::retrial(exchange=true). Table movement can remove responder ownership before actual Room::retrial, preventing its conditional second CardResponded. Do not merge these two differently flagged events or treat the ask flag as implementing judgment replacement.

## Design choices to align before code

- **A, recommended:** add a bounded None/Discard request operation (two explicit method values), sharing the room-wide provided state and stable acquisition contracts while keeping existing MethodUse/Response APIs unchanged. Reject retrial=true for now, explicitly deferring acquisition-only retrial plus judge replacement/package orchestration. Keep None/Discard acceptance focused and separately review this seam.
- **B:** include acquisition-only isRetrial support across the request methods in this slice, while still deferring actual Room::retrial and package judgment orchestration. More complete askForCard coverage, but touches existing MethodUse/Response control flow and requires new compatibility/impact checks. Report the acquisition option precisely, never as complete retrial support.
- **C:** implement the complete retrial/judge pipeline and Guicai/Guidao composition together with None/Discard. This combines unrelated selection costs, judge exchange, result updates and package event policy. Defer until a separate source-backed design and its state contracts are approved.

A shared generic dispatcher or new normalized operation is an implementation choice only after boundary approval; existing callback fixtures and request admission should not become a newly permissive client API. No change to scheduler, resource readers or Standard production registration follows from this research.

## Acceptance cases

1. Real scheduler dispatch/resume for both methods sets UNKNOWN reason/pattern, clears continuing, emits no CardAsked, and returns accepted original validated identity. Assert MethodNone permits a Slash pattern and performs no automatic payment, use/response/finish event or after-hook.
2. Shared room-wide provide covers null/non-null, duplicate rejection, dead actors, cross-method nested consumption and validation-null retry. MethodNone ignores generic card limitation rejection by native policy; MethodDiscard retains method-specific AI/provided limitations and human-adapter admission. Preserve original-to-validated conversion and rich metadata/reference identity.
3. For None, ChoiceMade may run children or mutate the response metadata, but there is no movement/history/reveal/card-skill notice after it. Compose a caller-owned subsequent action to show the request has not consumed the selected card.
4. For Discard, compare nonempty versus empty request skillName. Capture physical/log material IDs before ChoiceMade; alter the validated current material set during ChoiceMade and prove movement uses the post-choice material set. Verify response log/emotion/broadcast and owned-card-skill notice are absent.
5. Assert one real direct-to-discard atomic movement, S_REASON_THROW(actor), no automatic skill/general/event metadata, all materials together, no table intermediate, zero-material virtual no-op, and no double move when child events redirect movement. isProvision=true still discards. Preserve current movement's actual cancellation/rewrite rules.
6. Nil selection emits nil ChoiceMade and returns null. Validation-null emits no ChoiceMade for that failed conversion, retains eager effects, resets skillName/provision and retries. Empty skillName after retry must eliminate its former discard log/request-skill notice.
7. JSON suspend/restore across selection/validation/notifications/ChoiceMade/movement must not repeat effects; wrong actor/stale/replayed prompt and registry mismatch keep scheduler protection. Current interruption behavior retains eager effects and freezes unfinished frames; native exception unwind remains deferred.
8. If option A, reject retrial=true and unsupported methods before execution and document pending retrial. If option B, test the distinct guards above, preserving existing ordinary use/response behavior and making no claim about judge replacement or package event completion.
