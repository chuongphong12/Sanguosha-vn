The game uses eight synthetic physical cards, two living adjacent seats with 4 HP each, a fixed seat-0 Play context and one plain Slash allowance. Availability, reference metadata and no-skill hooks are fixture authorities. There are no production catalogues, skills, equipment, conversions, full turns, lethal/rescue integration or native deck-manifest claims. The current clock-v3 prototype save identity rejects older v1/v2 scratch saves.

## Command, commit and receipt

The [session owner](https://github.com/chuongphong12/Sanguosha-vn/blob/816191df12e6b9b5849b727104afd4a350d58ca9/server/prototypes/hegemony-m0/session.ts) authenticates the secret-bound seat, live controlling tab and generation before accepting a normalized draw/play/answer command. New intent requires the current game revision. Answer intent contains only the prompt ID and offered choice; the server supplies card metadata, materials and actor authority.

Commands and scheduled work serialize through one local writer and share actual Master execution. Master storage/subscriber/transport output is staged; raw Master packets are discarded. Game state, pending scheduler frames, RNG state, metadata, controller generation, clock state, per-seat bot memory and receipts are saved together by the default file write → fsync → rename or the optional atomic SQL UPDATE. Only after commit can the transport return a fresh actor projection. This persistence boundary stages library mutations; it does not change the library's eager child/late-error semantics. Automatic receipts use a separate server-only namespace that public intent IDs cannot forge.

Receipt identity includes the normalized payload. An identical accepted intent retry returns its receipt and current actor view; the same ID with another prompt/choice is a collision. Controller authorization still precedes receipt lookup. A new stale intent, wrong actor/prompt, unoffered Jink or prior controller cannot resume the pending decision. Unrelated drawing is rejected while the scheduler is occupied.

The default store is a same-machine scratch file with a local PID writer lease. An optional separate PostgreSQL process is now exercised through the store boundary below. These establish neither power-loss/hosted-provider durability, general distributed failover nor a durable event outbox. Serialized RNG state is present, but this slice has no shuffled-draw progression/recovery proof.

## Projection, transport and bot

The [loopback transport](https://github.com/chuongphong12/Sanguosha-vn/blob/816191df12e6b9b5849b727104afd4a350d58ca9/server/prototypes/hegemony-m0/transport.ts) binds commands to its socket's authenticated seat and does not register stock lobby/sync handlers. Unknown/deleted rooms do not implicitly recreate. Last-online explicit Leave deletes the room even with another offline member; an explicitly departed credential loses its return right. Permanent replacement of an explicitly departed member is still absent; retained offline members have the bounded takeover behavior below.

Actor views allow only own hand, public hand counts/HP/discard/outcome names and owner-only choices. Raw frames, tags, resources, RNG, private request data and opponent hand identities are excluded. A secondary same-seat tab sees the same actor information read-only; explicit takeover advances generation and fences the prior controller.

The [pure bot policy](https://github.com/chuongphong12/Sanguosha-vn/blob/fbe60f6b911956d2b432840f0cfe8970218acd35/server/prototypes/hegemony-m0/bot.ts) receives only an actor observation and versioned per-seat memory. The session invokes it automatically for the current pending plain Jink or cancellable Play request; accepted results and memory are committed together. This is not an autonomous full-turn worker or a competitive-strength result.

## Service-time deadlines and recovery

The [clock boundary and deadline model](https://github.com/chuongphong12/Sanguosha-vn/blob/fbe60f6b911956d2b432840f0cfe8970218acd35/server/prototypes/hegemony-m0/deadlines.ts) use a trusted monotonic clock, with no network tick/advance command. Each new prompt gets sixty seconds. Disconnect starts a separate sixty-second seat deadline and does not reset the prompt. An online prompt expiry executes one bot decision while retaining human control/generation. Offline grace expiry transfers the retained seat to bot control and advances generation; reconnect/control claim can restore human control at the serialized boundary. Current prompt and authority are checked again before scheduled execution. Any live authenticated same-seat tab preserves presence.

Room lifetime has a third deadline: the last passive human disconnect starts sixty seconds, after which the room is deleted before bot work. Bots cannot preserve an empty room. Recovery preserves saved prompt/seat remainders and starts a fresh sixty-second room return window from service readiness. A previously online member starts a new offline episode; an already offline member retains its saved seat remainder. Startup and server downtime are excluded from these service-time clocks.

The default owner schedules a checkpoint every second while rooms exist, persists elapsed uptime, and publishes only committed actor views. `timing` exposes own control and own committed prompt remainder; private bot memory and other actors' choices remain hidden. Write failure publishes no new state. File storage can retry; SQL uncertainty fences the writer and requires restart/reload. Failed recovery releases its store ownership. Mutating requests drain already-due work before processing the new action, preventing a reconnect from bypassing a due deletion merely because a callback has not run.

Only successfully checkpointed uptime survives shutdown/crash. A one-second scheduling interval is not a hard precision bound under queue, CPU or disk delay; uncommitted uptime can be given back, with a larger gap during failed checkpoints. Exact crash-time accounting, timing SLOs and external-provider durability are not proven by this local prototype.

## Separate PostgreSQL storage proof

The [store boundary](https://github.com/chuongphong12/Sanguosha-vn/blob/816191df12e6b9b5849b727104afd4a350d58ca9/server/prototypes/hegemony-m0/storage.ts) owns acquire/read/write/authority/close. The file adapter remains the default; failure to open an explicitly selected store does not fall back to file or memory. The [PostgreSQL adapter](https://github.com/chuongphong12/Sanguosha-vn/blob/816191df12e6b9b5849b727104afd4a350d58ca9/server/prototypes/hegemony-m0/postgres.ts) holds a session advisory lock on one direct Client connection for a server namespace. It writes the complete private document in one atomic UPDATE conditional on the loaded SQL revision. A second writer is refused. A changed revision, observed connection loss or query/commit failure fences that writer, including cached views and commands. Restart acquires a new connection and reloads committed state/receipts; an uncertain commit is never replayed from cached state.

The [dedicated proof](https://github.com/chuongphong12/Sanguosha-vn/blob/816191df12e6b9b5849b727104afd4a350d58ca9/tests/prototypes/m0-postgres.proof.ts) runs actual Socket.IO actors against disposable local PostgreSQL. It covers process kill while Jink is pending, response commit before lost ACK, a failed SQL constraint, actual database restart with the old game server alive, stale SQL revision and deletion/rejected resurrection. It is a separate Docker-required command, not silently skipped ordinary CI. Source tests and the [execution checkpoint](../reviews/2026-10-26-hegemony-m0-postgres.md) have distinct roles.

This is a local SQL experiment, not a chosen/accepted hosted provider. It requires a direct/session connection rather than transaction pooling. No automatic owner transfer/reconnect worker, external outbox, multi-node failover or physical-erasure guarantee for SQL/WAL/backups is implemented. Existing clock precision and fixture limits still apply.
