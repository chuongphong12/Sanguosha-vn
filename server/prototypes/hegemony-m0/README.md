# THROWAWAY M0 local tracer and bot baseline

Question: can an application-owned session stage the installed boardgame.io Master, commit its state and receipt together, then expose only actor views? Can a small actor-only TypeScript policy use that same command boundary?

This branch is an investigative source artifact, not a production implementation or a full Quốc Chiến match. The user approved the session contract at Q31 and continuing with a real Slash → Jink prompt. Its [contract](../../../knowledge/research/2026-10-22-m0-session-contract.md) and existing rules authority remain in force. These executable slices do not complete either M0.3 or M0.4.

## Run

- `npm run prototype:m0`: starts the loopback-only demo and prints its address and scratch-state path. Two private browser contexts represent different people; another tab of the same context can restore its stored seat. Restart with `npm run prototype:m0 -- /absolute/path/to/PROTOTYPE-wipe-me-…/rooms.json` to reuse that scratch state. The parent directory must exist. Delete that scratch directory when finished.
- `npm test -- tests/prototypes`: local kernel/session/privacy checks, including an actual killed server process.
- `npm run prototype:m0:browser`: installed Playwright Chromium, two isolated browser contexts plus a second tab, real HTTP/Socket.IO. This is separate from ordinary unit CI because it needs an installed browser.
- `npm run prototype:m0:benchmark`: emits raw local chooser and staged-Master draw measurements. Machine metrics are a baseline, not a latency/bot-strength acceptance threshold.
- `npm run prototype:m0:postgres`: dedicated real PostgreSQL/Socket.IO failure proof. Requires a running local Docker daemon; pulls a pinned official PostgreSQL image, creates a uniquely named scratch container bound only to loopback, and removes that container/volume on completion. This is separate from `npm run check`; absence of Docker fails this command instead of silently skipping SQL evidence.

The demo needs its local server because real Socket.IO and disk recovery are the questions under test. It deliberately supersedes the prototype skill's default no-server/no-tests shape; the approved tickets explicitly require real transport/storage and privacy/fault checks. No production route imports this code. `server/server.ts`, existing engine modules and their registration are unchanged.

## PostgreSQL experiment

The session owns a small `SessionStore` boundary: acquire/open, read the complete saved document, atomically write, check writer authority, close. Existing file storage stays the default and retains its fault/recovery tests. Set server-only `M0_DATABASE_URL` and `M0_STORE_NAME` to run the same loopback demo against a **scratch** PostgreSQL database; no connection string is logged or projected. It creates only the `prototype_m0_sessions` experiment table. Use a direct PostgreSQL connection, not a transaction-pooling endpoint: the writer holds a session advisory lock until its connection closes. The driver uses its normal connection-string/TLS verification; no certificate-verification bypass is installed.

One atomic SQL update persists the complete state/deadlines/authority/memory/receipts document with a revision condition. Another writer for that namespace is refused. A changed revision, lost connection, query failure or uncertain commit fences this writer, including cached views and commands. Restart the game server to acquire a new connection and reload the committed document; it must not retry an uncertain command from cached state. Duplicate accepted commands are then resolved by the existing payload-bound receipts. There is no automatic reconnect/owner-transfer worker or external notification outbox.

The dedicated proof uses two actual socket actors, kills game-server processes during pending Jink and after response commit before ACK, injects a real SQL constraint failure, restarts PostgreSQL while the old server remains alive, changes the stored revision to exercise stale-writer rejection, and restores after last-human deletion. SQL failure publishes no speculative engine result. A single dedicated connection/document is a prototype coordinator choice, not proof of a hosted provider's connection pool, failover, capacity, quotas or power-loss behavior. Tests use disposable local PostgreSQL, not Neon/Render; no vendor, account, deployment, billing or paid service is selected here. SQL row-version/WAL/backup retention is not a secure-erasure guarantee for deleted rooms.

## Clock authority and precision

Only the trusted session clock supplies monotonic time; clients have no tick/advance RPC. Deadlines and elapsed service time persist in the same document as engine effects. The default owner checkpoints at one-second scheduling intervals while rooms exist and checks due work before mutations. Actor views expose only their committed remaining decision time/control mode; callbacks and bot memory stay private. Timer-triggered publication is queued after durable commit.

Restart creates a new monotonic origin at readiness, never a wall-clock delta from the last save. Existing prompt/offline deadlines retain their saved service-time remainder; the room receives a fresh 60-second readiness recovery grace so retained humans can return. Any human return clears the all-offline room grace. Bot control does not count as an online human or preserve an abandoned room.

Only successfully checkpointed uptime survives a process stop. Uncommitted uptime may be given back, and background wakeup/commit/queue latency delays a timeout. The one-second scheduling interval is not a hard upper bound under storage/CPU delay. Failed file writes publish no speculative result and retry later; SQL uncertainty fences the writer and requires restart/reload. Failed recovery initialization releases its store ownership. Exact crash-time accounting, hosted-provider availability/transaction semantics and production timing SLOs remain unproven.
